# 为 Windows ChatGPT 启用单美元符号公式渲染

部分 Windows ChatGPT 版本内置了 KaTeX，却没有启用 `$...$` 形式的行内公式。对于这类版本，可以修改本地前端的 Markdown 解析规则，让 `$x^2$` 生成公式节点，再交给应用自带的 KaTeX 渲染。

这种方法需要定位当前版本的解析代码、维护资源完整性记录，并从可写目录中的应用副本启动。它适用于公式引擎已经存在、问题出在分隔符识别的情况。

## 确认公式在哪里被忽略

公式显示通常经过以下过程：

```text
消息文本 → Markdown 解析器识别公式分隔符 → 生成公式节点 → KaTeX 渲染
```

先在同一条消息中比较 `$x^2$`、`\(x^2\)` 和 `$$x^2$$`。如果其他分隔符能正常显示，只有单美元符号不生效，应重点检查解析器的分隔符规则；如果公式已经生成但显示异常，则应检查渲染错误、样式和字体。

Windows 桌面应用可能使用 Electron 打包，前端资源位于应用目录的 `resources/app.asar`。定位时应结合运行中进程的可执行文件路径、应用包清单和资源内容，确认实际使用的版本。包名、显示名称和内部版本号可能不同。

使用支持 ASAR 格式的工具列出、读取资源，在 JavaScript 中搜索 `singleDollarTextMath`、公式分隔符正则以及 KaTeX 调用，再沿调用位置确认消息正文使用的解析路径。资源文件名通常带构建哈希，不宜把某个版本的文件名作为固定入口。

## 修改分隔符识别规则

Markdown 扩展可能分别实现“查找下一个公式起点”和“从当前位置解析公式”。两处规则需要一致，否则即使解析函数接受单美元符号，前面的起点搜索也可能跳过它。

下面是一种压缩代码中的修改示例，变量名和正则结构需以当前版本为准：

```diff
- e.match(/^(?:\\\(|\\\[|\${2,})/)
+ e.match(/^(?:\\\(|\\\[|\${1,})/)

- e.search(/\\(?:\(|\[)|\${2,}/)
+ e.search(/\\(?:\(|\[)|\${1,}/)
```

这里将美元符号的最少数量从两个改为一个，保留原有的反斜杠分隔符规则。还应检查对应的闭合分隔符、转义处理，以及行内公式和独立公式的区分逻辑。

同一个应用也可能有多条 Markdown 渲染路径。其中某条路径通过选项控制单美元符号识别：

```diff
- singleDollarTextMath: false
+ singleDollarTextMath: true
```

压缩后的对应写法可能是：

```diff
- singleDollarTextMath:!1
+ singleDollarTextMath:!0
```

`!1` 表示 `false`，`!0` 表示 `true`。应修改已经确认用途的规则和配置，避免对整个资源包中的相同文本盲目替换。

上述示例的修改前后字节数相同，适合在原位置替换，可以保持 ASAR 内文件的长度和偏移不变。如果修改改变了字节数，就需要使用 ASAR 工具重新打包并生成正确的目录结构和偏移。

## 同步维护 ASAR 完整性记录

修改前先备份原始 `app.asar` 和对应的启动程序，记录应用版本、文件 SHA-256、修改位置及修改前后的内容。备份应放在补丁目录之外，并通过哈希确认与原文件一致。

部分 Electron 构建启用了 ASAR 完整性检查。此时，仅修改 JavaScript 即使保持长度不变，也会因哈希不匹配而启动失败。需要检查当前构建的完整性设置，并依次更新：

1. ASAR 头中被修改文件的完整性信息，包括文件哈希和分块哈希。
2. 应用启动程序中保存的 ASAR 头哈希。

计算顺序是先完成资源修改，再更新 ASAR 内的文件完整性信息，最后根据新的 ASAR 头更新启动程序中的记录。哈希范围、分块大小、头部序列化格式和记录位置必须遵循当前版本的打包方式，不能用整个 ASAR 文件的哈希代替头哈希。

在某些 Windows 构建中，启动程序资源里保存了以十六进制文本表示的 SHA-256。应通过资源结构和原始头哈希的对应关系定位它，确认匹配后再替换。不能依赖其他版本的固定偏移，也不能仅凭出现一段 64 位十六进制字符串就认定它是目标记录。

完成后重新读取资源，核对修改内容和完整性信息，并保存补丁文件的完整哈希。这样可以保留应用原有的完整性检查机制。

修改可执行文件会使其原有 Authenticode 签名无法继续验证修改后的内容；更新 ASAR 哈希不会重新获得发布者签名。

## 从可写目录中的副本运行

商店应用通常安装在受保护的 `WindowsApps` 目录。可以将完整应用目录复制到当前用户可写的位置，在副本上应用补丁，并保留商店原版作为日常切换和恢复入口。

应复制完整应用目录，因为启动程序还依赖运行库、资源和其他文件。写入补丁前，核对副本中的目标文件与备份一致；写入后，再核对补丁哈希。启动时通过进程的实际可执行文件路径确认运行的是副本。

应用脱离商店包后能否正常运行，需要检查该版本对包标识、运行库和启动环境的依赖。副本可以打开窗口，也仍需验证登录、原有对话访问和需要使用的应用功能。

如果希望副本继续使用原有登录状态和本地设置，应先确认原应用的用户数据目录，并查明该版本支持的路径配置方式。Electron／Chromium 常见的参数是 `--user-data-dir`，应用也可能在启动代码中自行设置路径，因此需要检查实现及运行结果。在部分构建中可以找到 `CODEX_ELECTRON_USER_DATA_PATH` 环境变量，但应先确认当前版本确实读取它。

复用原用户数据前先备份该目录；切换版本时先完整退出正在运行的实例，避免两个进程同时访问同一份数据。启动后结合日志和实际生成的文件确认数据目录生效。

为副本创建独立快捷方式，明确设置可执行文件、工作目录，以及经过确认的启动参数或环境变量。若需要启动脚本，应让快捷方式调用该脚本，保留原商店入口以便切回。

副本的所有启动入口应使用同一个用户数据目录。Electron 的单实例锁与用户数据目录关联：如果一个快捷方式通过脚本指定原数据目录，另一个却直接运行可执行文件并使用默认目录，就可能同时启动两个独立实例，表现为多出一个 ChatGPT 主窗口。

检查开始菜单、桌面和任务栏中指向副本的快捷方式，将它们统一到同一启动脚本，或设置相同的目标、工作目录和用户数据参数。修改前备份快捷方式的目标、参数、工作目录及图标；更改环境变量时，应确保它们传给实际启动的应用进程。

## 验证解析结果与实际界面

验证应覆盖解析、渲染和应用启动三个层面。

解析测试尽量使用应用当前版本实际包含的 Markdown 解析器、公式扩展和 KaTeX，检查：

- 单美元符号公式：幂、分式、中文句子中的公式、同一段中的多个公式。
- 其他分隔符：`\(...\)`、`\[...\]`、`$$...$$` 和跨行公式。
- 容易误判的文本：行内代码、代码块、转义美元符号、未闭合分隔符，以及一个或多个价格金额。

单美元符号也用于货币，尤其要检查包含多个金额的句子。其处理结果取决于解析器的边界和闭合规则，不能只用一个孤立金额判断是否存在误识别。

渲染测试检查公式是否生成 KaTeX 节点、是否出现错误节点、字体是否成功加载，并实际查看分式、上下标等排版。只看到解析函数返回了 HTML，还不足以确认显示正常。

最后启动补丁副本，确认进程路径、用户数据目录和窗口状态，检查日志中是否存在 ASAR 完整性错误，再打开真实对话查看原先无法渲染的公式。如果应用包含多条正文渲染路径，应分别覆盖相应场景。

还应依次重复使用各个启动入口，检查主进程 PID 是否保持不变，以及是否新增主窗口。Electron 会创建渲染、GPU 等子进程，因此应结合命令行区分主实例，不能直接用进程总数判断。若仍有窗口自行出现，记录出现时间，并对照进程启动时间、命令行和窗口日志继续定位。

## 恢复与更新

切回商店原版时，先退出副本，再通过原入口启动。如果需要恢复副本，应将同一版本备份中的 `app.asar` 和启动程序配套恢复，并核对哈希；两者通过 ASAR 头哈希关联。

撤除副本时，退出应用后删除副本及其快捷方式即可；改写过的已有快捷方式可从备份恢复。若副本复用了原用户数据目录，应保留这份数据。

商店原版更新后，独立副本通常仍停留在旧版本。需要更新副本时，应从新版重新复制，重新检查解析规则、资源结构和完整性记录，完成验证后再调整快捷方式。补丁和备份都应按版本保存，避免将旧版文件或固定偏移应用到新版。
