# 提炼收获

这次实验只有一次训练、67 次参数更新，对"AZR 自博弈能否提升推理能力"本身得不出结论。下面保留两条，都不依赖训练的随机性：第一条关于评分指标，来自对已保存回答的重新评分；第二条汇集过程中的工程问题。

## 一、卡格式的评分会把"学会输出格式"记成能力提升，还会盖住真实的退步

评估沿用了训练时的评分方式：回答必须严格写成"`<think>…</think>`，紧接 `<answer>…</answer>`"，否则直接记 0 分。按这个评分，67 次更新后 CruxEval 两项合计从 15.6% 涨到 39.5%。

把同一批回答不卡格式地重新评分后，结论反了过来：

- **上涨全部来自格式。**训练前模型多数时候已经给出了答案，只是没写标签。输出预测训练前格式合规率只有 12.5%，不卡格式的正确率却有 50.0%。训练后格式合规率接近 100%，合计正确率 39.5%，低于训练前不卡格式的 44.5%。
- **同一时间真实能力在下降。**输出预测不卡格式的正确率从 50.0% 降到 35.2%（128 题中 29 题由对变错、10 题由错变对，配对检验 $p = 0.003$），而官方评分显示的是从 5.5% 涨到 35.2%。回答长度同步缩到原来的四分之一左右，逐步代入求值的过程变成了几句概括。

所以这个指标不只是夸大了提升，它让一次退步看起来像是六倍的进步。这一点只取决于评分方式和已保存的回答，换一个随机种子重新训练也不会改变。

**可迁移的做法：**

- 做任何"训练前后对比"之前，先单独看训练前模型的格式合规率。合规率低时，训练前的分数量的是"会不会写标签"，不能当作能力的起点。base 模型（非 instruct）遇到要求特殊标签的提示，尤其容易出现这种情况。
- 每个评估点同时报告三个数：格式合规率、卡格式的正确率、不卡格式的正确率。再加一个固定子集的对照：只看训练前格式就已合规的题，这部分题的分数不受"格式从不合规变合规"的影响。本实验里这个子集上的分数基本不变（输入预测 33 → 36 题，输出预测 7 → 9 题），与不卡格式评分的结论一致。
- 每个评估点保存逐题回答原文，并记录回答长度。这次能在事后分清"格式"和"能力"，靠的就是每次评估都落盘了逐题回答；回答长度的骤降则是推理过程被压缩的直接信号。
- 训练前的分数低得不合常理时（一个代码模型在"给程序和输入求输出"上只有 5.5%），先读几条回答，再相信这个数。

## 二、工程问题

这次实验在两处遇到问题，原因都在运行环境而非方法本身。

1. **日志里学习率正常，不代表参数在更新。**AZR 所用的训练框架里，常数学习率调度在 warmup 步数为 0 时，第一次参数更新实际使用的学习率是 0；而日志是在调度器前进一步之后才读取学习率的，所以显示的是设定值 $10^{-6}$。只跑一两步的连通性测试因此会出现"梯度范数正常、日志学习率正常、参数一个都没变"的情况。

   **可迁移的做法：**让 agent 做"训练能否跑通"的连通性测试时，要求它直接比较更新前后的权重，而不是看损失、梯度范数和日志里的学习率。在测试脚本里加一个"保存的权重与初始权重不同"的断言，成本很低，能挡住这类静默失效。

2. **在共享 GPU 上，训练中途释放显存的设计会被别人的任务截断。**这套框架让推理引擎（vLLM）和训练共用同一批 GPU：每次采样结束后推理引擎休眠并释放显存，下一次采样前再唤醒、重新申请。在多人共用的机器上，这段空窗期内显存可能被别人的任务占走：这次训练就是这样中断的，另一位用户的任务在空窗期占用了其中两张卡，推理引擎唤醒时申请不到显存而报错退出，丢掉了约 2 小时的训练。改成让推理引擎常驻、不再休眠之后，后续的 57 次更新没有再出现这个问题；代价是显存峰值更高，因为推理和训练的占用叠在了一起。

   **可迁移的做法：**只要训练进程要与别人的任务共用 GPU，就不能把"释放过的显存还能拿回来"当前提；能常驻就常驻，并把保存间隔按"一次中断能接受损失多少"来定，而不是沿用默认值。
